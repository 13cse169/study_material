Git Basics

Installation, setup & fundamental commands

What is Git?

Git is a distributed version control system (DVCS) created by Linus Torvalds in 2005. It tracks changes in source code and allows multiple developers to collaborate without overwriting each other's work.

🔀
Version Control
Track every change ever made to your codebase
🤝
Collaboration
Multiple developers working simultaneously
🔄
Branching
Experiment without breaking main code
🛡️
Backup
Distributed — every clone is a full backup

Core Commands

bash
git init               # Initialize new repo
git clone <url>        # Clone remote repository
git status             # Show working tree status
git add <file>         # Stage a file
git add .             # Stage all changes
git commit -m "message" # Commit staged changes
git commit -am "msg"  # Stage tracked + commit

Example: Initialize a repo and make your first commit

bash — step by step
# 1. Create project directory
mkdir my-project && cd my-project

# 2. Initialize git repository
git init
# Output: Initialized empty Git repository in .git/

# 3. Create a file
echo "# My Project" > README.md

# 4. Check status
git status
# Output: Untracked files: README.md

# 5. Stage the file
git add README.md

# 6. Make first commit
git commit -m "Initial commit: add README"

Interview Questions

What is Git and how does it differ from other VCS?
Git is a distributed version control system (DVCS). Unlike centralized VCS (SVN, CVS), every developer has a full copy of the repository including its history. This enables offline work, faster operations (most are local), and no single point of failure. Git uses snapshots rather than delta-based storage.
What is the difference between Git and GitHub?
Git is the version control system — the tool installed on your computer. GitHub is a cloud-based hosting service for Git repositories. GitHub adds collaboration features (pull requests, issues, CI/CD, GitHub Actions) on top of Git. Alternatives to GitHub include GitLab and Bitbucket.
What does git init do vs git clone?
git init creates a brand-new empty repository in the current directory (creates a .git folder). git clone <url> copies an existing repository from a remote server including all history, branches, and files.
Quick Quiz — Git Basics
Which command stages ALL changed files for the next commit?

Module 02

Working with Changes

Staging, diffs, logs and history

The Three Trees

┌──────────────────┐ git add ┌──────────────────┐ git commit ┌──────────────────┐ │ Working Directory│ ──────────► │ Staging Area │ ──────────► │ Repository │ │ (your files) │ │ (Index) │ │ (.git folder) │ │ │ ◄────────── │ │ ◄────────── │ │ └──────────────────┘ git restore └──────────────────┘ git restore └──────────────────┘ --staged
  • Working Directory — Your actual project files. Files can be modified, untracked, or ignored.
  • Staging Area (Index) — A preview of your next commit. You selectively add changes here.
  • Repository — The .git database. Committed history lives here permanently.

Viewing Changes: diff, log, show

bash
# Show unstaged changes
git diff

# Show staged changes (ready to commit)
git diff --staged

# Show commit history
git log

# Compact one-line log
git log --oneline --graph --all

# Show specific commit details
git show <commit-hash>

# Who changed what and when
git blame filename.js

Example: Track file changes step-by-step

bash
# Modify a file
echo "New feature" >> app.js

# See what changed (unstaged)
git diff
# Output: + New feature

# Stage the change
git add app.js

# See what's staged
git diff --staged

# Commit it
git commit -m "feat: add new feature"

# View history
git log --oneline

Interview Questions

What is the staging area in Git?
The staging area (also called the Index) is an intermediate zone between the working directory and the repository. It lets you selectively choose which changes to include in your next commit. This is powerful because you can work on multiple things and only commit related changes together.
What does git diff do and what are its variants?
git diff shows changes between working directory and staging area (unstaged changes). git diff --staged shows changes between staging area and last commit. git diff HEAD shows all changes since last commit. git diff branch1 branch2 compares two branches.
Quick Quiz — Changes
Which command shows changes that are staged (ready to commit)?
git diff
git diff --staged
git status --diff
git log --changes
Module 03

Branching

Create, switch, merge branches like a pro

What Are Branches?

A branch is a lightweight, movable pointer to a commit. Branching lets you diverge from the main line of development and work independently without affecting others.

Branch Commands

bash
# List all branches
git branch

# Create a new branch
git branch feature/login

# Switch to branch (old way)
git checkout feature/login

# Switch to branch (modern way)
git switch feature/login

# Create AND switch in one command
git switch -c feature/login

# Merge branch into current branch
git merge feature/login

# Delete a merged branch
git branch -d feature/login

# Force delete unmerged branch
git branch -D feature/login

Example: Create a feature branch and merge it

bash
# 1. Create and switch to feature branch
git switch -c feature/user-auth

# 2. Make your changes and commit
git add .
git commit -m "feat: add user authentication"

# 3. Switch back to main
git switch main

# 4. Merge feature branch
git merge feature/user-auth

# 5. Delete the feature branch
git branch -d feature/user-auth

Interview Questions

What is a branch in Git?
A branch in Git is a lightweight movable pointer to a specific commit. When you create a new branch, Git creates a new pointer — it doesn't copy files. The default branch is typically called "main" (or "master" in older repos). HEAD is a special pointer that tells Git which branch you're currently on.
What is the difference between merge and rebase?
Merge integrates two branches by creating a new "merge commit," preserving full history. Rebase replays your commits on top of another branch, creating a linear history. Merge is safer for shared branches; rebase is preferred for feature branches to keep history clean. Never rebase public/shared branches.
Quick Quiz — Branching
Which command creates a new branch AND switches to it in one step?
git branch -new feature
git checkout --branch feature
git switch -c feature
git create feature
Module 04

Remote Repositories

Push, pull, fetch — collaborate via GitHub/GitLab

Remote Commands

bash
# Add a remote
git remote add origin https://github.com/user/repo.git

# List remotes
git remote -v

# Push to remote (first time)
git push -u origin main

# Push to remote (after tracking is set)
git push

# Fetch without merging
git fetch origin

# Pull (fetch + merge)
git pull origin main

# Pull with rebase
git pull --rebase origin main

Example: Push a local repo to GitHub

bash
# 1. Create repo on GitHub (via website), then:
git remote add origin https://github.com/youruser/project.git

# 2. Rename branch to main (if needed)
git branch -M main

# 3. Push and set upstream tracking
git push -u origin main

# 4. Future pushes are just:
git push

Interview Questions

What is the difference between git fetch and git pull?
git fetch downloads changes from the remote but does NOT integrate them into your working branch. Your local work is untouched. git pull is essentially git fetch + git merge — it downloads AND merges remote changes into your current branch. Use fetch when you want to review changes before merging.
What does git push -u origin main do?
The -u flag sets the upstream tracking reference. This means future git push and git pull commands will automatically know which remote branch to use without specifying origin main each time. It links your local main branch to origin/main.
Quick Quiz — Remote
git pull is equivalent to which two commands?
git push + git merge
git fetch + git merge
git clone + git merge
git fetch + git rebase
Module 05

Collaboration Workflow

Pull requests, forks, code reviews

Pull Requests & Forking

A Pull Request (PR) is a GitHub/GitLab feature to propose changes. It enables code review before merging into the main branch. A Fork is a personal copy of someone else's repository — standard for open source contributions.

bash — fork-based workflow
# 1. Fork on GitHub UI, then clone your fork
git clone https://github.com/YOU/project.git
cd project

# 2. Add the original as upstream
git remote add upstream https://github.com/ORIGINAL/project.git

# 3. Create your feature branch
git switch -c fix/typo-in-readme

# 4. Make changes, commit, push to your fork
git add . && git commit -m "fix: correct typo"
git push origin fix/typo-in-readme

# 5. Open a Pull Request on GitHub UI
# 6. Keep your fork in sync with upstream
git fetch upstream
git merge upstream/main

Interview Questions

What is a pull request and why is it important?
A pull request is a way to propose changes to a codebase. It notifies team members of pushed changes and allows them to review, discuss, and request modifications before the code is merged. PRs are fundamental to modern collaborative development — they catch bugs, enforce standards, and share knowledge. Despite the name, it's really a request to "merge" not to "pull."
What is the difference between a fork and a branch?
A branch exists within the same repository. A fork is a complete copy of the repository under your own account. Branches are used within a team on the same repo; forks are used when contributing to projects you don't have write access to (open source). Both ultimately use PRs to integrate changes.

Module 06

Undo & Fix Mistakes

reset, revert, restore — never lose your work

Reset, Revert, Restore

bash
# --- RESTORE (safe, no history change) ---
# Discard working directory changes
git restore filename.js

# Unstage a file (keep changes)
git restore --staged filename.js

# --- REVERT (safe, creates new commit) ---
# Undo a commit by creating a new "undo" commit
git revert HEAD
git revert <commit-hash>

# --- RESET (destructive!) ---
# Soft: moves HEAD, keeps staging + files
git reset --soft HEAD~1

# Mixed (default): unstages, keeps files
git reset HEAD~1

# Hard: DESTROYS changes — use with caution!
git reset --hard HEAD~1

Example: Undo last commit safely

bash
# Option 1: Keep changes, unstage them
git reset --soft HEAD~1
# Changes are still staged — re-commit when ready

# Option 2: Keep files, unstage everything
git reset HEAD~1
# Files are modified but unstaged

# Option 3: Create a safe "undo" commit (for pushed commits)
git revert HEAD
# Creates a new commit that undoes the last one

Interview Questions

What is the difference between git reset and git revert?
git reset rewrites commit history by moving the HEAD pointer backward — it modifies history, making it dangerous for shared branches. git revert creates a NEW commit that is the inverse of the target commit, preserving history. Always use revert on shared/public branches, and reset only on local/private branches.
What is the difference between --soft, --mixed, and --hard reset?
--soft: moves HEAD only. Changes remain staged. --mixed (default): moves HEAD and unstages changes. Files are unmodified. --hard: moves HEAD, unstages, AND discards all changes. Files are reset to match the commit. Hard reset is the most destructive.
Quick Quiz — Undo
Which is the SAFE way to undo a commit that has been pushed to a shared remote?
git reset --hard HEAD~1
git reset --soft HEAD~1
git revert HEAD
git restore HEAD
Module 07

Advanced Branching

Rebase, cherry-pick, squash commits

Rebase, Cherry-pick & Squash

bash
# --- REBASE ---
# Rebase current branch onto main
git rebase main

# Interactive rebase — edit last 3 commits
git rebase -i HEAD~3

# --- CHERRY-PICK ---
# Apply a specific commit from another branch
git cherry-pick <commit-hash>

# Cherry-pick a range of commits
git cherry-pick abc123..def456

# --- SQUASH (via interactive rebase) ---
# Opens editor: change 'pick' to 'squash' (s)
git rebase -i HEAD~4
# In editor: pick, squash, squash, squash
# This combines 4 commits into 1

Example: Rebase a feature branch onto main

bash
# 1. Make sure main is up to date
git switch main && git pull

# 2. Switch to your feature branch
git switch feature/my-feature

# 3. Rebase onto main
git rebase main
# Your commits are now "replayed" on top of main

# 4. Resolve any conflicts if they arise
# Then: git add . && git rebase --continue

# 5. Force push (ONLY if this is YOUR branch)
git push --force-with-lease

Interview Questions

When should you use rebase vs merge?
Use merge when integrating feature branches into main — it preserves the historical context of when branches diverged. Use rebase on your own local feature branch to incorporate upstream changes, keeping history linear and clean. Golden rule: never rebase a branch that others are working on.
What is cherry-pick used for?
Cherry-pick applies a specific commit from one branch to another without merging the whole branch. Use cases: applying a hotfix to multiple release branches, pulling a specific bug fix without taking all other changes from a feature branch, or rescuing work from a branch that's been abandoned.

Module 08

Stashing

Save work temporarily without committing

Stash Commands

bash
# Stash current changes
git stash

# Stash with a description
git stash push -m "WIP: user profile page"

# Also stash untracked files
git stash -u

# List all stashes
git stash list

# Apply most recent stash (keeps it in list)
git stash apply

# Apply AND remove from stash list
git stash pop

# Apply a specific stash
git stash apply stash@{2}

# Drop a stash
git stash drop stash@{0}

# Clear all stashes
git stash clear

Example: Switch branches without losing work

bash
# You're mid-work on feature branch when urgent bug comes in
git stash push -m "WIP: dashboard redesign"

# Switch to main, fix the bug
git switch main
# ...fix bug, commit...

# Return to feature branch
git switch feature/dashboard

# Restore your stashed work
git stash pop

Interview Questions

What is git stash and when would you use it?
git stash temporarily shelves (stashes) changes you've made to your working directory so you can switch context without committing incomplete work. Common scenarios: you need to switch branches to fix an urgent bug, pull new changes (to avoid conflicts), or test something on a clean state. The stash is a stack, so you can have multiple stashes.
What is the difference between git stash pop and git stash apply?
Both apply the stash to the working directory. git stash pop applies AND removes it from the stash list. git stash apply applies it but keeps it in the stash list. Use apply when you want to apply the same stash to multiple branches.
Quick Quiz — Stashing
Which command applies the most recent stash AND removes it from the stash list?
git stash apply
git stash pop
git stash get
git stash restore
Module 09

Tags & Releases

Version your software with semantic tagging

Tag Commands

Tags mark specific commits as important — typically release points (v1.0.0). There are two types: lightweight (just a pointer) and annotated (with metadata — preferred for releases).

bash
# Create annotated tag (recommended)
git tag -a v1.0.0 -m "Release version 1.0.0"

# Lightweight tag (no metadata)
git tag v1.0.0-lw

# Tag a specific past commit
git tag -a v0.9.0 <commit-hash> -m "Beta release"

# List all tags
git tag

# Show tag details
git show v1.0.0

# Push a tag to remote
git push origin v1.0.0

# Push ALL tags
git push origin --tags

# Delete a tag locally
git tag -d v1.0.0

# Delete remote tag
git push origin --delete v1.0.0

Interview Questions

What are tags in Git and what are the two types?
Tags are references pointing to specific commits, used to mark release points. Lightweight tags are just a name pointing to a commit (like a branch that doesn't move). Annotated tags are stored as full objects in the Git database and contain tagger name, email, date, and a message. Annotated tags are recommended for releases as they include more metadata and can be signed.
Quick Quiz — Tags
Which command creates an annotated tag for v2.0.0?
git tag v2.0.0
git tag -a v2.0.0 -m "Release"
git release v2.0.0
git annotate v2.0.0
Module 10

Git Internals

Blobs, trees, commits and the HEAD pointer

Git Object Model

Git is fundamentally a content-addressable filesystem. Everything is an object stored in .git/objects/, identified by a SHA-1 hash.

📄
Blob
Stores file content. No filename, just content. Two identical files share one blob.
🌳
Tree
Represents a directory. Points to blobs and other trees with filenames.
📦
Commit
Points to a tree (snapshot), parent commits, author, and message.
🏷️
Tag Object
Annotated tag — points to a commit with metadata.
HEAD → main → Commit [abc123] │ ├── tree [def456] (root directory) │ ├── blob [aaa111] → README.md │ ├── blob [bbb222] → app.js │ └── tree [ccc333] → src/ │ └── blob [ddd444] → index.js │ └── parent: [prev-commit]
bash — inspect internals
# See HEAD position
cat .git/HEAD

# Show object type
git cat-file -t <hash>

# Show object contents
git cat-file -p <hash>

# List tree contents
git ls-tree HEAD

Module 11

Expert Level

Merge conflicts, Git workflows, best practices

Merge Conflict Resolution

Merge conflicts occur when two branches modify the same line of a file. Git marks the conflicting sections and you must resolve manually.

conflict markers
<<<<<<< HEAD (current branch)
const greeting = "Hello, World!";
======= (separator)
const greeting = "Hi there!";
>>>>>>> feature/greeting (incoming branch)
bash — resolve flow
# 1. Attempt merge
git merge feature/greeting
# CONFLICT! Open file and resolve markers manually

# 2. Edit file to keep the right version, then:
git add filename.js

# 3. Complete the merge
git commit
# Git auto-generates a merge commit message

# Abort a merge in progress
git merge --abort

Git Workflows

Git Flow uses two main branches: main (production) and develop (integration). Feature, release, and hotfix branches serve specific purposes.

Branches: main, develop, feature/*, release/*, hotfix/* main ──────────────────────────────────► v1.0 ── v1.1 ↑ ↑ develop ──── feature/A ──────────────► release/1.1 └── feature/B ──┘ │ hotfix/bug ──┘
  • Feature branches from develop
  • Release branches for stabilization
  • Hotfix branches from main
  • Best for scheduled release cycles

Trunk-Based Development — everyone commits to a single main branch (trunk) with very short-lived branches. Relies heavily on feature flags.

main ─── A ─── B ─── C ─── D ─── E ──► └─ feat ─┘ (max 1-2 days)
  • Continuous integration is mandatory
  • Feature flags control unfinished features
  • Small, frequent commits reduce conflicts
  • Best for high-velocity CI/CD teams

Monorepo — all projects in a single repository. Used by Google, Facebook, Microsoft.

  • Easier cross-project refactoring
  • Shared build/lint/test configs
  • Requires tooling: Nx, Turborepo, Bazel
  • Challenges: large repo size, complex CI
structure
my-monorepo/
├── apps/
│   ├── web/
│   └── mobile/
├── packages/
│   ├── ui/
│   └── utils/
└── package.json

Git Best Practices

  • ✅ Write clear, concise commit messages (use Conventional Commits: feat:, fix:, chore:)
  • ✅ Make small, atomic commits — one logical change per commit
  • ✅ Always pull before pushing to avoid conflicts
  • ✅ Use .gitignore from the start — never commit secrets or build artifacts
  • ✅ Never force-push to shared/protected branches
  • ✅ Use branch protection rules on main/production branches
  • ✅ Prefer revert over reset for public commits
  • ✅ Review diffs before every commit: git diff --staged
  • ✅ Use SSH keys instead of passwords for authentication
  • ✅ Sign commits with GPG for verified identity
